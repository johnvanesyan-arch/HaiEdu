# Governed whole-form mastery selection

This implementation adds the explicit blueprint sibling `masteryFormSelection` without changing the exact `assessmentPolicy` v1 object or the existing unconfigured dynamic mastery algorithm. The schema is `haiedu-mastery-form-selection-v1`, strategy `ordered-unseen-whole-form-v1`, with an ordered `formIds` array.

The actual configured form count must cover the bound lifecycle's maximum attempt count. Each form must be active, protected, in the same pool, completely inside the version-bound blueprint, have exactly the policy's per-skill counts, and be disjoint from all other declared forms. Form version, item version and skill identities are frozen in a private immutable snapshot keyed to the assessment policy binding. Binding after learner use of an unconfigured blueprint, snapshot drift, removing the opt-in, retired content, or cross-purpose eligibility fail closed. A new reviewed blueprint/form version is required for a replacement. Reserve items are never substituted automatically.

The launcher selects the first whole form with no historical assignment, exposure event or attempt for any constituent item, across purposes/releases. The atomic starter rechecks the full selected form and history before inserting the header/items and attaching the unchanged mastery lifecycle. Existing active sessions resume first. Read-only status validates without creating bindings, lifecycle rows, learner sessions or fence updates.

Every governed launch, atomic start and session operation uses a learner-wide transaction advisory lock before session/pool locks. Exposure inserts use it before consulting the binding registry, covering a first uncommitted binding. Private durable learner/item/form/pool fence rows force serialization failures when a Repeatable Read mutation's old snapshot cannot see a just-committed binding or reservation. Pool membership writers share a parent-pool row lock and pool fence with pool-scope changes, including the first uncommitted member of an empty pool. Opt-in selection itself requires Read Committed (the API default). No coordination rows are seeded by the migration; they are created only by actual subsequent configuration/runtime transactions.

Runtime consumers: `start-learning-session`, `get-session-item`, `submit-answer`, `submit-mastery-answer`, `get-remediation-help`, `get-mastery-check-status`, and `get-chapter-mastery-lifecycle` import the unchanged governed runtime router. `record-recommendation-event` and `get-student-classes` also import its unchanged session-claim helper. The router calls the replaced database RPCs; no Edge import/source edit or deployment is needed for this slice. Private session locking is also used by the unchanged resume, operation and recommendation-event RPCs. New unavailable-form errors retain the existing generic HTTP 403 `learning_context_unavailable` projection. Existing known lifecycle errors retain their mappings.

This bounded rollout does not extend whole-form assignment enforcement to legacy pre-governed RPCs. The actual Chapter II allocation must have no overlap with legacy Chapter I blueprint/pool eligibility; the current Chapter I selectors resolve Chapter I snapshots/skill IDs and cannot choose the new Chapter II IDs. Ordinary historical public-read exposure is not inferred from this runtime history check and remains separately recorded in the owner's pilot disposition.

Verification: 16 focused PGlite tests cover complete three-attempt/review lifecycle, form-level history skipping, exhaustion without reserve substitution, atomic stale-history/mixing checks, version/configuration drift, incorrect coverage/disjointness, pool eligibility protection, protected serving, another subject's unchanged dynamic behavior, read-only writes and RPC privileges. The existing governed runtime tests also passed. The configuration agent independently verified the actual 16-item/eight-skill policy: 13/16 with every skill represented passes; 12/16 fails; 14/16 with zero correct for one skill fails.

The committed independent PostgreSQL connection suite covers first binding versus other-pool eligibility, first binding/assignment versus exposure in both orders, duplicate/resume/rollback, retirement, staged and empty-pool scope changes, and stale Repeatable Read form/pool/exposure mutations. Local native PostgreSQL could not start because the host runs UID 0 without account-creation/setuid capabilities; therefore these races require the configured PostgreSQL 17.6 CI job before deployment. No production mutations were made by this implementation task.
