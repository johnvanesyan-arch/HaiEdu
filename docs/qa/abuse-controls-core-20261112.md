## Implemented behavior

The fixed candidate policies are the four budgets in the [audited proposal](abuse-controls-audit-20261112.md): ordinary app activity, session starts, code/token redemption and recipient-weighted invitation email attempts. They are test policies, not current live settings. Each counter belongs to the actor's UUID and a fixed policy key, independently of tabs, session rotation, school address, class, role, subject or grade. One actor may spend several budgets together; either all are reserved or none are spent.

The counter uses integer microseconds of virtual debt to implement a token bucket without floating-point drift. It allows a bounded initial burst and refills at the documented rate, rather than imposing a fixed-window maximum. It reads the real database clock after waiting for locks. An actor transaction lock serializes concurrent workers even when their counter rows do not exist yet; policy/row locks use canonical order. An advisory-hash collision can briefly share a lock, but never an allowance or state key. Old repeatable-read snapshots fail serialization rather than inventing a fresh allowance.

Denied requests return a positive `retryAfterSeconds` without spending another policy, creating a counter row, updating its expiry or appending an event. This preserves a stable waiting period and bounds denial-related storage writes. Ordinary app activity uses a different budget from code redemption, so a code-attempt cooldown does not itself consume the app allowance.

The server-only reserve wrapper accepts an already verified actor UUID and positive integer costs from the fixed registry. Unknown keys, malformed costs, missing actors and costs exceeding a burst are rejected. The actor has an Auth-user foreign key and deletion cascades its counters. Private tables have RLS and no direct grants to public, client or service roles. The private implementation has a fixed `pg_catalog` search path and a narrow security-definer capability; its public wrapper is security-invoker. Only the trusted service role can execute it. That role cannot edit the policy registry or directly reset/read counter tables through the new grants.

This primitive does not authenticate or authorize a person. A future handler must derive the actor from its existing verified identity and retain every live-session, role, school/recipient, ownership, subject-neutral learning and content check before doing protected work. Do not pass actor IDs, arbitrary policy names, costs or clocks straight from a browser request. No role, tenant, subject or school receives a bypass in this core.

## Commit and cleanup boundaries

The reservation is transactional, not autonomous. Its server caller must commit the reservation in a separate RPC/database transaction before starting a fallible business operation. The tests explicitly prove both outcomes: rolling back the reservation itself removes it; failure in a later, separate business transaction does not refund the committed attempt. Do not move the reservation inside an invitation/redemption transaction that raises and rolls back its own failure count. Recipient reservations count attempts; this component does not send or refund mail.

Counter storage has one row per actor/fixed-policy pair. Idle expiry is 24 hours for the current test registry, long enough for every candidate burst to refill. Cleanup checks both expiry and full refill, uses an expiry index and `SKIP LOCKED`, and deletes at most 500 rows per call (default 200). It does not block a locked active row or delete an unrefilled allowance merely because a fixture marks its expiry old. No background schedule has been installed. Counters store no IP addresses, supplied codes, invitation tokens, email addresses or learner responses.

## Verification

Thirteen embedded PostgreSQL/PGlite semantic tests pass: access grants, weighted/multi-budget reservations, stable denial state/row versions, actor independence, invalid inputs, bounded refill, backward-clock debt, independent business failure, transaction rollback, cleanup, account-deletion cascade, fixed registry and search-path restrictions. The component's production isolation is part of the fixture design: it accepts no external URL or production credential.

Fourteen checks also pass on actual PostgreSQL **17.6**, with independent connections. They cover missing-row and existing-state races, reversed budget order, real-clock refill, a real lock wait, stale-snapshot serialization, separate business rollback, browser-role denial, service policy restrictions, cleanup contention/batch bounds and account-deletion races. Concurrent code attempts admit exactly ten requests before refill; concurrent 20-recipient reservations admit five batches, 100 synthetic recipient attempts total. No SMTP request is made.

The actor-isolation scenario submits 120 logical actors through up to 24 independent database connections. Exhausting one actor's code allowance leaves ordinary app use and the other 119 actors/teacher available. The counter has no IP parameter. This proves independent counter state, not 120 simultaneous provider sign-ins, browser sessions, a shared-network Auth limit or classroom throughput. Those separate BF-21/BF-24 staging qualifications remain open.

A private negative control removes the actor transaction lock from an in-memory copy of the SQL and forces overlapping reads. It admits 40 code attempts against the ten-token burst, demonstrating the missing-row race that the shipped component prevents. That defective SQL is not committed or deployed; the production project is never contacted by the control. The initial focused SQL run and actual PostgreSQL run pass on their first attempt. Raw logs and the negative-control driver are retained privately.

The existing `phase3-postgres-17` CI job now runs the real counter concurrency suite. The existing PostgreSQL service/version, credentials/production refusal, five required jobs, aggregate dependencies, pinned Actions, browser job and production-QA guards are preserved. No new production permission, dependency, secret or workflow dispatch is added. The full local repository suite passes 1,816 tests on its first attempt, with zero failures, skips or cancellations; this includes the 13 new semantic cases. Browser syntax/Python compilation, whitespace and the existing QA dependency guard pass. All five exact-head hosted jobs remain required before merge; see [PR476 checks](https://github.com/johnvanesyan-arch/HaiEdu/pull/476/checks). Existing browser cases are not counter/UI integration acceptance. A registered migration, target-schema rehearsal and relevant Supabase advisor checks remain future delivery work.
